# Инженерные решения Smart Meal AI

## Публичный срез и ветки

Рабочий код сервисов развивается в `develop`. Ветка `main` используется как
стабильная публичная точка входа: там README, описывающий состояние `develop`.


## Асинхронная генерация

Генерация меню может занимать существенно больше обычного времени HTTP-запроса.
Поэтому сценарий моделируется через задачу: клиент получает `task_id` и отдельно
получает состояние и результат. Задача хранится в PostgreSQL, воркер забирает её
через `FOR UPDATE SKIP LOCKED`, а не держит соединение всё время генерации.

## Единая точка входа и доверие внутри контура

Наружу опубликован только gateway. Он проверяет JWT, сам подписывает токены
(ES256) и передаёт сервисам идентификатор пользователя в `X-User-Id`, срезая
клиентское значение этого заголовка. Внутренние сервисы токен не проверяют: их
защищает сетевая изоляция. Такой компромисс выбран вместо mTLS между сервисами.

## Отзыв токенов в Redis

JWT не хранится в БД, но logout должен немедленно лишать токен силы. Поэтому
gateway пишет `revoked:{jti}` в Redis со сроком жизни до `exp`. Если Redis
недоступен, защищённые маршруты отвечают 503: считать токен отозванным нельзя,
считать его действительным — тоже.

## Разделение сервисов

Пользовательские данные, рецепты, справочники и маршрутизация имеют разные зоны
ответственности. Это упрощает командную разработку и позволяет менять AI-логику,
не распространяя её детали на gateway и клиентское приложение. Справочники
неизменяемы в рантайме и обновляются миграцией: клиент выбирает только их `id`.

## Локальная модель вместо внешнего провайдера

Генерация выполняется Ollama на собственной GPU. Промпт собирается из шаблона,
параметров пользователя и последних лайков и сохраняется в задаче при создании,
поэтому смена шаблона не влияет на уже поставленные в очередь задачи. Ответ
валидируется: не меньше трёх блюд, без дублей и пустых строк. Невалидный ответ
повторяется, таймаут и недоступность модели — нет, иначе очередь встаёт на всё
время таймаута.

## Одна реплика

Сервисы рассчитаны на одну реплику: лимиты запросов gateway и лимит хэширования
паролей хранятся в памяти, воркер генерации — один asyncio-таск в процессе MS-4.
Это осознанное упрощение для текущего масштаба; для нескольких реплик нужны общий
счётчик в Redis и вынос воркера в отдельный процесс.

## Инфраструктура отдельно от бизнес-кода

Окружения, контейнеры, хранилища, Redis и эксплуатационные настройки находятся в
отдельном `smai-infra`. Секреты передаются через окружение и GitHub Secrets,
JWT-ключ раскладывается отдельным workflow с правами `0400` и владельцем UID 10001. В репозиториях хранятся только шаблоны `.env.example`.
